# 갱신계약 피처 추가 보고서 (평균보증금인상률 / 갱신계약비율 / 갱신요구권행사비율)

`data/전세보증대위변제현황_피처추가.xlsx`(10컬럼, 50,054행)에 국토교통부 전월세 실거래가 API로
갱신계약 관련 피처 3개를 추가한 작업 전체 기록. 최종 산출물은
`data/전세보증대위변제현황_피처추가_갱신피처.xlsx`(14컬럼, 50,054행).

---

## 1. 신규 컬럼 정의

| 컬럼 | 계산 방법 | 왜 유용한가 |
| --- | --- | --- |
| **평균보증금인상률** | `(deposit - preDeposit) / preDeposit` 평균. `contractType='갱신'`이면서 `preDeposit>0`인 계약만 대상 | 보증금을 급격히 올리는 지역은 갭투자·무자본갭투기 패턴과 연관 |
| **갱신계약비율** | `contractType='갱신'` 비율. `contractType`이 공백(정보없음)인 행은 분모에서 제외 | 신규 계약 비중이 높은 지역일수록 신축 갭투자 유입 가능성 ↑ |
| **갱신요구권행사비율** | `useRRRight='사용'` 비율 (전체 계약 대비) | 임차인이 계약갱신청구권을 쓴 비율 — 낮으면 임대인이 신규 세입자로 자주 교체하는 지역일 수 있음 |

세 컬럼 모두 개별 계약(`일련번호`) 단위로 계산할 수 없다. 실거래가 데이터가 계약 단위이긴 하지만
`대위변제현황` 데이터의 `일련번호`와 직접 매칭할 키(주소, 계약일 등)가 없기 때문에,
**(시도, 주택구분, 보증완료월) 단위로 집계한 값을 같은 그룹의 모든 행에 공통으로 부여**하는 방식을 썼다.

## 2. 사용한 API와 수집 방법

### 2-1. API 4종
국토교통부 전월세 실거래가 API(공공데이터포털, 서비스그룹 `1613000`), 4종을 전부 호출:

| API | 엔드포인트 |
| --- | --- |
| 아파트 | `RTMSDataSvcAptRent` |
| 연립다세대 | `RTMSDataSvcRHRent` |
| 단독다가구 | `RTMSDataSvcSHRent` |
| 오피스텔 | `RTMSDataSvcOffiRent` |

이 API들에만 `contractType`(신규/갱신), `useRRRight`(갱신요구권 사용여부), `preDeposit`(종전보증금),
`deposit`(신규보증금) 필드가 있어서 반드시 필요했다.

### 2-2. 수집 범위
- **기간**: 2022-01 ~ 2024-12 (36개월, 학습데이터 기간과 동일)
- **지역**: 17개 시도 전체를 시군구 단위로 훑으면 호출량이 너무 많아(250개 시군구), **시도당 대표
  시군구 1곳**을 샘플링 (`renewal_features/lawd_codes.py`)
- **주택구분 매핑**: 아파트→apt, 다세대/연립→rh, 오피스텔→offi, 다가구/다중/단독/주상복합→sh(근사)
  (`renewal_features/house_type_map.py`)
- 총 17개 시도 × 36개월 × 4개 API = **2,448회 호출**

### 2-3. 파이프라인 (3단계)
1. `fetch_realprice.py` — 위 2,448개 조합을 실제 호출해서 `raw_transactions.csv` 생성 (서비스키 필요,
   이 코드실행 환경은 `apis.data.go.kr` 접근이 막혀있어 사용자 로컬 PC에서 실행)
2. `build_renewal_features.py` — raw 데이터를 (시도,주택구분,연월) 단위로 집계, 세분화 단계별
   (`fine`/`coarse`/`national`) 대체값 파일 생성
3. `merge_renewal_features.py` — 원본 xlsx에 3개 컬럼 merge, 어느 단계에서 채워졌는지
   `갱신피처_출처` 컬럼에 기록

## 3. 데이터 수집 중 발생한 이슈

실제로 여러 차례 시행착오를 거쳤다. 정리하면:

### 3-1. `useRRRight` 필드 인코딩이 예상과 다름
처음엔 `useRRRight`가 `'Y'`/`'N'`으로 인코딩되어 있을 거라 가정했는데, 실제로는
**`'사용'` 또는 공백(`' '`)** 이었다. 이 때문에 갱신요구권행사비율이 초기에는 항상 0으로
계산되는 버그가 있었고, 이를 발견해서 수정했다.

### 3-2. `contractType` 공백값 처리
`contractType`도 `'신규'`/`'갱신'` 외에 공백(`' '`, 정보없음) 값이 있었다 (연도별 38,606건(2022)
→ 30,880건(2023) → 7,037건(2024)로 감소 추세 — 신고 데이터 완성도가 시간이 갈수록 개선된 것으로
추정). 공백을 신규로 잘못 세면 갱신계약비율이 과소평가되므로, 갱신계약비율 계산 시
분모에서 제외했다.

### 3-3. data.go.kr 응답 스키마 이슈
인증/권한 문제가 있을 때 이 API는 HTTP 200이지만 `response` 키 대신 `cmmMsgHeader`로 에러를
담은 완전히 다른 JSON 구조를 반환하는 경우가 있다. 처음엔 이걸 그냥 "결과 0건"으로 처리해서
실패가 성공처럼 기록되는 버그가 있었다. 이를 감지해서 예외로 처리하도록 고쳤는데, 그 과정에서
**이 API의 성공 코드가 `"00"`이 아니라 `"000"`(0이 3개)** 라는 것도 뒤늦게 발견해서 두 번 수정했다.

### 3-4. 중복행
여러 차례 재시도하며 실행하는 과정에서 완전 중복행이 28,000~31,000건(전체의 7~8%) 발생했다.
`build_renewal_features.py`에서 로드 직후 자동으로 `drop_duplicates()` 처리하도록 했다.

### 3-5. 인천 대표 시군구 재선정
처음 인천 대표 시군구로 중구(LAWD_CD 28110)를 썼는데, 학습기간(2022~2024) 전체에서
`totalCount=0`으로 응답했다 (원도심이라 아파트 전월세 거래량 자체가 매우 적은 지역).
**연수구(28185, 송도국제도시)로 교체**해서 정상적으로 데이터를 받았다.

### 3-6. 광주·전남은 끝내 수집 불가
광주 동구(29110)→광산구(29200), 전남 목포시(46110)→여수시(46220)로 대표 시군구를 바꾸고
2022-01/2023-12/2024-06 세 시점을 다 테스트해봤지만 **학습기간 전체에서 계속 0건**이었다.
원인을 조사한 결과, **2026-07-01(정확히 이번 작업 진행 중 발생)에 광주광역시와 전라남도가
"전남광주통합특별시"로 행정통합**되었고, 이로 인해 법정동코드 체계가 개편되면서 이 실거래가
API가 기존(구) 코드로는 데이터를 못 찾는 것으로 추정된다. 신규 코드 체계가 아직 충분히
알려져 있지 않아 더 이상 추적하지 않고, **광주·전남은 전국평균(national)으로 대체**하기로 결정.

### 3-7. 진행 재개(resume) 로직 추가
실행이 중간에 끊기거나 특정 조합만 실패하는 일이 반복되어, `fetch_realprice.py`가 매 호출마다
`<out>.progress.csv`에 성공/실패를 기록하고, 재실행 시 이미 성공한 조합은 건너뛰도록 만들었다
(`bootstrap_progress.py`는 구버전 결과물에서 이 진행기록을 역산해주는 보조 스크립트).

## 6. 간단 검증

```
평균보증금인상률          대위변제여부=0: 0.558   대위변제여부=1: 0.623
갱신계약비율              대위변제여부=0: 0.180   대위변제여부=1: 0.168
갱신요구권행사비율         대위변제여부=0: 0.062   대위변제여부=1: 0.054
```

대위변제여부와의 상관계수는 각각 0.008 / -0.042 / -0.056으로 **신호가 약하다**. 방향성은
있다 — 갱신계약비율·갱신요구권행사비율이 낮은(=임대인이 세입자를 자주 교체하는) 지역에서
대위변제 비율이 소폭 높다 — 는 가설과 일치하지만, 단독으로는 예측력이 크지 않다. 기존
`전세가율`(상관계수 0.242), `주택유형위험도`(0.215)에 비해 신호가 약하므로, 모델링 시
보조 피처로 활용하되 큰 기대는 하지 않는 것이 맞다.

주택구분별 갱신계약비율은 아파트(20.3%) > 다세대(16.6%) > 연립(15.7%) > 오피스텔(13.2%) >
다중/다가구/주상복합/단독(7~10%) 순으로, 상식적인 방향(아파트일수록 갱신 비중이 높음)과 일치한다.

## 7. 한계 (발표자료에 명시할 것)
- 시도당 대표 시군구 1곳만 조회 (17개 시도 전체 시군구 조회는 호출량이 너무 많아 샘플링함)
- 개별 계약 단위 매칭이 아니라 (시도,주택구분,월) 집계값을 붙인 것 — 같은 그룹 내 모든 건에 동일 값 부여
- 다중주택/주상복합은 API에 대응 유형이 없어 단독다가구 API 값으로 근사
- **광주·전남은 전국평균으로 대체** — 2026-07-01 광주-전남 행정통합 이후 법정동코드 개편으로
  추정되는 이유로 API 응답이 0건
- `평균보증금인상률`에 극단치 존재 (최대 2786%대) — 원본 실거래가 데이터의 이상치가 그룹평균에
  반영된 것. 모델링 전 winsorize 등 이상치 처리 권장
- 대위변제여부와의 단순 상관관계는 약함 (0.01~0.06 수준) — 단독 예측력보다는 보조 피처로 활용

## 8. 재현 방법
`renewal_features/README.md` 참고. 요약하면:
```bash
python fetch_realprice.py --start 202201 --end 202412 --out raw_transactions.csv
python build_renewal_features.py --in raw_transactions.csv --out renewal_features.csv
python merge_renewal_features.py --base ../data/전세보증대위변제현황_피처추가.xlsx \
    --out ../data/전세보증대위변제현황_피처추가_갱신피처.xlsx
```
