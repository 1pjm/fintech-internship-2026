# Part A. 이론 확인 — 설계 전에 언어를 맞추자
## A-1. 혼동행렬을 업무 언어로 (Slide 10)
내 시나리오 기준으로 네 칸을 **업무 문장**으로 바꿔 보세요. “TP = True Positive” 같은 정의 반복은 금지입니다.
| 항목 | 교과서 정의 | 내 시나리오에서 실제로 벌어지는 일 |
| --- | --- | --- |
| TP | 사기를 위험으로 예측 | 시세조종 리딩방을 선제적으로 파악하여 개인 투자자의 피해를 막았다 |
| FP | 정상을 위험으로 예측 | 합법 유료 리서치·투자정보 방을 리딩방으로 잘못 표시하여 신뢰 문제 및 민원 발생 |
| FN | 사기를 정상으로 예측 | 리딩방에서 개인 투자자가 피해를 보는 일이 발생한다 |
| TN | 정상을 정상으로 예측 | 합법 정보방에 오안내로 인한 피해를 주지 않는다 |
- 작성 예시 — 중고거래 플랫폼이라면
    
    
    | 항목 | 내 시나리오에서 벌어지는 일 |
    | --- | --- |
    | TP | 사기 판매글을 결제 전에 검토 큐에 올려 피해를 막았다 |
    | FP | 정상 판매자의 글이 노출 제한되어 판매 기회를 잃고 문의가 들어온다 |
    | FN | 사기 판매글이 그대로 거래되어 구매자가 돈을 잃고 신고·환불 분쟁이 생긴다 |
    | TN | 정상 판매자를 방해하지 않고 거래가 끝났다 |
## A-2. 지표는 세 층으로 본다 (Slide 11)
각 층의 빈칸을 채우세요.
| 층 | 대표 지표 | 답하는 질문 |
| --- | --- | --- |
| (모델) 품질 | Precision, Recall, F1, PR-AUC | 점수가 사기와 정상을 얼마나 구분하는가? |
| 운영 품질 | 경보량, Precision@K, P95 조치시간 | 사람이 이 경보를 (제때) 처리할 수 있는가? |
| 데이터·통제 품질 | 커버리지, 신선도, 결측률 | 입력 정보와 보호 절차가 (믿을) 만한가? |
- 예시 답안
    
    순서대로: **모델 / 제때 / 믿을**
    
    핵심(Slide 11): 모델 지표가 좋아도 경보가 너무 많거나 정보가 늦으면 실제 예방 성과는 낮을 수 있습니다. 그래서 오늘 Part D에서 지표를 한 층이 아니라 **세 층에서 하나씩** 고릅니다.
    
## A-3. 점수, threshold, 정책은 서로 다르다 (Slide 9)
각 문장이 셋 중 무엇에 대한 말인지 적으세요. (점수 / threshold / 정책)
| 문장 | 무엇에 대한 말인가 |
| --- | --- |
| “이 거래는 72점입니다” | 점수 |
| “70점 이상을 고위험으로 봅니다” | threshold |
| “70~84점은 추가 인증, 85점 이상은 일시 보류합니다” | 정책 |
- 예시 답안
    
    순서대로: **점수 / threshold / 정책**
    
    자주 하는 오해(Slide 9): 점수를 곧 차단 명령으로 여기거나, F1이 가장 높은 threshold 하나를 정답으로 여기는 것. 모델은 신호를 정렬하고, **고객과 서비스에 미치는 영향은 정책이 결정**합니다.

# ⭐ Part B. 테이블 설계 구체화 — 시나리오를 스키마로
50회차에서 “이런 데이터를 모을 수 있겠다”고 나열했다면, 오늘은 **실제 테이블 한 장**으로 만듭니다. 52회차에 코드로 구현할 때 이 표가 그대로 설계도가 됩니다.
## B-1. 한 행(row)은 무엇인가 — 분석 단위 정하기
가장 먼저 정할 것은 컬럼이 아니라 **한 행의 정의**입니다.
| 질문 | 내 답 |
| --- | --- |
| 내 테이블의 한 행은 무엇인가? (거래 1건 / 판매글 1개 / 로그인 1회 / 계정 1개 / 청구 1건 …) | 공개 채널(방) 1개 - 백필한 메시지를 채널 단위로 집계한 한 세트 |
| 왜 그 단위인가? (탐지·조치가 일어나는 순간과 일치하는가?) | 탐지·조치(워치리스트·제보)가 '방' 단위로 일어나기 때문
메시지 단위는 너무 작고, 세력 단위는 관찰 불가 |
| 하루에 대략 몇 행이 쌓일 것 같은가? (자릿수만: 백 / 천 / 만 / 십만 / 백만) | 실시간이 아니라 '백필'이라 하루 개념은 약함. 시드 채널 기준 십~백 행(채널), 원본 메시지는 천~만 건 |
> 작성 팁: 조치가 일어나는 순간이 기준입니다. “결제 승인 순간에 막고 싶다”면 한 행은 결제 1건,
“판매글 등록 순간에 거르고 싶다”면 한 행은 판매글 1개가 자연스럽습니다.

## B-4. 불균형 추정과 Accuracy 착시 손계산 (Slide 7~8)
내 시나리오에서 양성(사기·이상)이 얼마나 드물지 추정하고, 그 비율로 착시를 직접 계산해 봅니다.
| 질문 | 내 답 |
| --- | --- |
| 전체 행 중 양성(라벨=1)은 몇 %쯤일 것 같은가? (교안 실습 데이터는 0.5%) | 약 (2)% |
| 그렇게 추정한 근거 (뉴스, 경험, 업계 상식 등 솔직하게) | 실제 텔레그램 크롤링(시드 11개 채널, 15,614건)에서도 아직 금감원 경보로 “확정”된 채널은 0건이라, 확정 라벨 기준 양성 비율은 이보다도 낮을 수 있음. 다만 시드 자체가 이미 리딩방으로 의심되는 채널만 골라 모은 편향된 표본이라, 감시 대상 전체(합법 정보방·개인 채널 포함)로 넓히면 2% 안팎이 보수적으로 합리적인 추정치라고 봄 |
이제 계산합니다. **전체 10,000행**이라고 가정하고 내 추정 비율을 넣으세요.
| 계산 | 내 답 |
| --- | --- |
| 양성 행 수 = 10,000 × 내 비율 | (200)건 |
| “전부 정상”이라고 예측하는 바보 모델의 Accuracy = (10,000 − 양성 수) ÷ 10,000 | (98)% |
| 이 바보 모델의 Recall | (0)% |
| 결론: 내 시나리오에서 Accuracy를 대표 지표로 쓰면 안 되는 이유 (한 문장) | 리딩방을 단 한 곳도 잡아내지 못하는 모델이 Accuracy 98점이라는 만점에 가까운 성적표를 받게 되므로, Accuracy는 이 문제에서 “모델이 잘하고 있다”는 착시만 만들 뿐 실제 탐지 성능을 대변하지 못한다 |
- 계산 예시 — 양성 0.5%로 추정했다면
    
    양성 = 10,000 × 0.005 = **50건** → 바보 모델 Accuracy = 9,950 ÷ 10,000 = **99.5%** → Recall = **0%**
    
    사기를 한 건도 안 잡는 모델이 99.5점을 받는 시험지라면, 그 시험지(Accuracy)가 잘못된 것입니다. 그래서 Part D에서 다른 지표를 고릅니다. 참고로 불균형은 **학습 데이터에서만** 보정(class weight, SMOTE 등)하고, 평가는 실제 비율 그대로 합니다. (Slide 17~18)

# Part C. 북극성 지표 정하기 — 우리가 진짜 지키려는 숫자
## C-1. 북극성 지표란
**북극성 지표(North Star Metric)**는 이 탐지 시스템이 존재하는 이유를 **하나의 숫자**로 나타낸 것입니다.
- Recall이나 Precision은 **수단**입니다. 그 자체가 목적이 아닙니다.
- 북극성은 고객·회사가 실제로 얻거나 잃는 것과 직결됩니다. 예: 월간 사기 피해 금액, 피해 예방 건수, 정상 거래 무마찰 통과율.
- Slide 21의 “좋은 해석”이 지표 → 비용 → 고객 경험 → 운영까지 말했던 것처럼, 북극성은 **성능지표를 업무 성과로 번역하는 기준점**입니다.

    | Precision@100 | 높아질수록 | 최근 오탐이 몰린 세그먼트(카테고리·가격대), 룰과 점수의 충돌 |
    | Recall@100 (라벨 확정 후) | 높아질수록 | K가 너무 작지 않은지, 고위험 유형이 큐 밖으로 새는지 |
    | 경보량(일) | 검토 용량 안으로 | threshold 또는 Top-K 설정, 특정 룰의 폭주 |
    | 필수값 채움률 | 높아질수록 | 수집 파이프라인 장애, 신규 유입 경로의 로그 누락 |
## D-4. 북극성 ↔︎ 성능지표 연결 문장
계기판과 목적지를 문장으로 연결합니다. 이 문장이 어색하면 D-2 선택이 잘못된 것입니다.
```

   북극성인 [금감원 경보 대비 사전 탐지율]가 [높아질]할 것이다.
   왜냐하면 검토 인력이 상위 K건 안에서 실제 조작 의심 채널을 더 정확히 확정해 워치리스트에 올릴수록, 경보가 뜨기 전에 이미 우리가 파악하고 있던 채널의 비율이 늘어나기 때문이다.
```
