# STEP 2. 02 전처리 설계 (33회차 흐름 그대로)

트랙 A라 **이미 짠 노트북 코드가 어느 단계에 해당하는지** 적었습니다. 33~44단계(수집·결측·중복·도메인 규칙·
사건 판정)는 이미 `telegram_fds_event.ipynb`가 끝냈으므로, `02_전처리.py`는 **스키마 검증과 자료형 정리만** 합니다.

| 단계 | 무엇을 확인·처리하나 | *예시(D 결제)* | 내 설계 |
|---|---|---|---|
| 1 불러오기·규격 | 필수 열이 다 있나 | *`encoding="utf-8-sig"`, 필수 8열 확인* | `encoding="utf-8-sig"`, `REQUIRED_COLUMNS` 20열(핵심 판정/게이트 열) 확인, 없으면 `ValueError` |
| 2 결측 | 어느 열이, 왜 비었나 | *`비고`만 빔 → MNAR → `""` 로 보존* | `press_basis_summary` = 뉴스 없음(MNAR, 보존). `low_tier_ratio` 결측은 분모(=`distinct_press`) 0 방어가 노트북에서 이미 됐는지 재확인 후 남으면 0.0으로 채움 |
| 3 중복 | 시스템 키 / **업무 키** | *업무 키 = `일시`+`PG사` → 0건* | 업무 키 = `event_id`(sha1 해시) → `drop_duplicates(keep="last")`, 실제 0건 |
| 4 도메인 규칙 | 업무적으로 불가능한 값 | *`성공+실패 = 시도`, 음수 금액* | 노트북 8~11단계에서 이미 처리(예: `post_data_status` 값셋 제한) — 여기서는 스키마만 재확인, 새 규칙을 추가하지 않음 |
| 5 변환 | 날짜형·범주 정리 | *`to_datetime`, `일자`·`시간대` 파생* | `event_anchor_at`/`event_start_at`/`event_end_at`을 `to_datetime`, `market_event_date`는 날짜만 정규화 |
| 6 파생변수 | 비교 가능한 **비율** | *`실패율`, `금액실패비중` (분모 0 방어)* | `event_date`(정렬·필터용 날짜 파생). `low_tier_ratio`는 노트북에서 이미 파생됨 — 02는 방어만 재확인 |
| 7 이상치 | IQR·도메인 → **보존 + 표시** | *IQR 상한 2.77% 초과 8행에 플래그* | `event_max_volume_ratio` 41배 같은 극단값을 지우지 않음 — 그것이 바로 "주의 패턴 관찰"을 찾는 이유 |
| 8 검증·저장 | 눈으로 확인 후 parquet | *행수·기간·결측 0 확인* | 행수(494)·기간(06-01~06-30)·`market_data_status` 분포(확인 434 / 부족+없음 60) 출력 후 `clean.parquet` 저장 |

**내 데이터의 업무 키**: `event_id` (텔레그램 세션 + 종목 + 사건 구간 기반 sha1 해시)
**분모가 0이 될 수 있는 비율**: `low_tier_ratio` (분모 = `distinct_press`. 관련 언론 보도가 전혀 없으면 0)

<details>
<summary>왜 7단계에서 지우지 않나</summary>

금융 데이터에서 이상치는 오류가 아니라 **오늘 우리가 찾으려는 사건**인 경우가 많습니다.
33회차 선택지 ③ *보존 + 표시* 를 씁니다. 판단은 03단계 규칙에 맡깁니다.
실제로 이 데이터에서는 **`event_max_volume_ratio` 상위권(41.7배 평균)이 그대로 '주의 패턴 관찰'
73건과 겹칩니다** — 지웠다면 가장 중요한 신호를 스스로 없앤 셈이 됩니다.

# STEP 3. 03 스코어링 설계 (40·41회차 공식 그대로)

```text
FinalScore = Gate × ( w1×점수1 + w2×점수2 + w3×점수3 )
```

> **이 프로젝트는 위 공식을 그대로 쓰지 않습니다.** PRD 9번 Scope의 설계 원칙이 "점수 없는 규칙 기반"을
> 명시하기 때문입니다. 아래 3-1~3-6은 템플릿의 자리에 **가짜 가중치를 채우는 대신, 실제로 쓰는 Gate ×
> boolean AND/OR 트리 구조를 정직하게 옮겨 적었습니다.**

## 3-1. ① 정규화 — 어떤 방식을 쓸 것인가

| 방법 | 언제 | 내 선택 |
|---|---|---|
| `minmax` (0~100) | 상대 비교·랭킹 | ☐ |
| 기준 대비 점수 (기준=50점) | 정책 기준선이 있을 때 = 모니터링 | ☐ |
| **구간 점수(Band)** | 정책상 구간이 딱 정해져 있을 때 | ☑ |

정규화 점수를 합산하지 않고, 각 규칙 통과 여부(boolean)를 조합해 **5개 상태(Band) 중 하나**를
직접 배정합니다(`classify_event()`). "몇 점인가"가 아니라 "어느 상태인가"로 답합니다 — 근거 배지
(`reason_badges`)가 정규화 점수 대신 "왜 이 상태인가"를 설명합니다.

## 3-2. ② Gate — 아예 판단에서 빼는 조건

| 항목 | *예시* | 내 설계 |
|---|---|---|
| Gate 조건 | *시도건수 ≥ 100* | `market_data_status == "확인"` (사건 구간 시장 데이터가 정상 확보됨) |
| 왜 필요한가 | *20건 중 1건 실패 = 5%. 비율이 튄다* | 시장 데이터가 없으면 거래량 배율·초과수익률 자체를 계산할 수 없어 어떤 판정도 근거가 없음 — "모른다"를 "정상"으로 둔갑시키지 않기 위해 |
| 통과 / 보류 건수 | *2,109 / 51* | 434 / 60 |
| 보류 행의 등급 이름 | *`판단보류`* | `판단 불가` |

> **Gate는 반드시 곱셈**입니다. 다른 점수가 아무리 높아도 Gate가 0이면 최종 0이어야 합니다.
> 그리고 보류를 `정상`이라고 부르면 안 됩니다. **"모른다"와 "괜찮다"는 다른 말입니다.**

## 3-3. ③ 가중합 → AND/OR 규칙 트리 (가중치를 쓰지 않는 이유)

| 규칙 이름 | 검사하는 열 | 기준 | 가중치 | 이 규칙이 뜨면 무엇부터 보나 |
|---|---|---|---|---|
| `market_concentration` (필수 AND) | `event_max_volume_ratio`, `event_volume_robust_z`, `event_peak_abnormal_return_pct` | 거래량 배율≥3.0배 **또는** MAD z-score≥3.5, **그리고** 사건구간 초과수익률≥7.0%p | 없음(필수 게이트) | 기준 중앙값 대비 거래량이 실제로 튀었는지, 코스닥 대비 초과 상승폭이 임계값을 넘었는지 |
| `post_decline` (보조 OR) | `post_relative_return_pct`, `post_max_drawdown_pct` | 사후 15거래일 상대수익률≤-10% **또는** 최대낙폭≤-15% | 없음 | 언급 후 실제로 코스닥 대비 하락했는지 |
| `multi_source_concentrated` (보조 OR) | `volume_concentrated & price_concentrated & news_concentrated` | 거래량·가격·뉴스 집중이 동시에 확인 | 없음 | 평소엔 없던 신호가 언급 시점에만 몰렸는지 |
| `material_disclosure_observed` (분기) | 공시 제목 키워드 | 중요 공시 후보 제목 관찰 | 없음 | **합계** | 공시 원문이 실제 중요 공시인지(정상 호재라는 뜻은 아님) |

> 가중치 칸이 전부 "없음"인 이유: PRD가 "적중률을 인위적으로 높이기 위해 위험 기준을 사후 조정하지
> 않는다"는 가드레일을 두고 있어, 튜닝 여지가 있는 가중치보다 **고정된 임계값 + AND/OR 조합**이
> 검증 가능성이 높다고 판단했습니다. 대신 5개 임계값 자체를 사이드바 슬라이더로 노출해 "이 기준이면
> 몇 번 울리는가"를 투명하게 보여줍니다(3-6).

## 3-4. ④ 검증 — 정답과 대조

| 항목 | *예시* | 내 결과 |
|---|---|---|
| 정답 라벨 열 | *`비고 == "장애"`* | 없음 — 관리종목 지정·상장폐지 등 실제 정답 라벨 미확보(PRD Open Issues) |
| 정답 쪽 평균 점수 | *94.4점* | "주의 패턴 관찰"군 사후 15거래일 상대수익률 평균 **-8.0%p** |
| 나머지 평균 점수 | *19.1점* | "특이 패턴 미관찰"군 사후 15거래일 상대수익률 평균 **+4.9%p** |
| 두 집단이 겹치는가 | *정상 최고 39.2 < 장애 최저 92.5 → 안 겹침* | 평균은 뚜렷이 갈리지만(약 12.9%p 차이) 개별 사건 단위로는 겹침 — 정답 라벨이 없어 "적중"이 아니라 **참고 근거**로만 씁니다 |

정답 라벨이 없다면: ☑ 상위 20건을 직접 눈으로 확인하고 "말이 되는가"를 적는다.
→ 실제로 확인한 결과, 거래량배율 상위 10건 모두 사후 상대수익률이 음수(-5.5%p ~ -58.8%p)였고,
최악 사건(사건ID `387375B5`)은 5개 채널 20회 언급 + 거래량 84.6배 + 사후 -58.8%p로 "말이 됨"을 확인.

## 3-5. ⑤ 등급 → 액션 → Reason Code

| 점수 구간(Band) | 등급 | 액션(누가 무엇을) | 내 데이터 건수 |
|---|---|---|---|
| Gate 미통과 | 판단 불가 | 핵심 시장 데이터 보강 후 재평가 | 60 |
| market_concentration만 | 단기 집중 패턴 관찰 | 사후 관찰을 계속 지켜본다 | 13 |
| market_concentration + 공시 | 공식 정보 동반 변동 | 공시 원문을 확인(정상 호재 확정 아님) | 15 |
| market_concentration + (사후하락 또는 복수신호) | 주의 패턴 관찰 | 근거 배지·뉴스·공시 원문을 사람이 직접 검토 | 73 |
| (그 외, market_concentration 미충족) | 특이 패턴 미관찰 | 정기 모니터링만 유지(안전 확정 아님) | 333 |

**Reason Code 문장 예시 3개** (경보 목록의 `판정 근거` 열에 그대로 들어갑니다)

1. 기준 중앙값 대비 거래량 이상; MAD 기준 거래량 이상치; 코스닥 대비 단기 초과상승; 언급 후 고점 대비 큰 하락; 복수 Telegram 채널 언급
2. 코스닥 대비 단기 초과상승; 언급 후 코스닥 대비 하락; 언급 시점 뉴스 집중; 포털 CP 매체 없이 저티어 매체에 광고성 표현 기사 집중(2건, 공시 미확인)
3. 시장 데이터: 기준 거래량 부족

## 3-6. ⑥ 기준 채점표

| 기준 후보 | 경보 건수 | 포착(사후하락 확인) | 놓침 | 헛경보(사후관찰 없이 복수신호로만) |
|---|---:|---:|---:|---:|
| 완화 (거래량≥2.0배 / 초과수익률≥5.0%p) | 85 | 84 | — | 1 |
| **기본값 (거래량≥3.0배 / 초과수익률≥7.0%p)** | 73 | 72 | — | 1 |
| 강화 (거래량≥5.0배 / 초과수익률≥10.0%p) | 61 | 60 | — | 1 |

> "포착"은 관리종목·상장폐지 같은 정답 라벨이 없어 **사후 15거래일 실제 하락 확인 여부**로 대체했고,
> "놓침"은 정답 라벨이 없어 계산할 수 없어 비워 둡니다(3-4와 동일한 한계).

**내가 고른 기준과 근거 한 문장**:
> 기본값(거래량 3.0배 / 초과수익률 7.0%p)을 유지한다 — 완화하면 경보가 85건으로 늘지만 사후하락
> 확인 비율(84/85≈98.8%)이 기본값(72/73≈98.6%)과 거의 같아 굳이 더 많은 사건을 사람이 검토할
> 이유가 없고, 강화하면 61건으로 줄어 실제 하락 사건 일부(예: 12건)를 조기에 놓칠 위험이 있다.
